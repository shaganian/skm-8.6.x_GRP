# План оновлення прошивки OTA

Проект: `skm-8.6.x\_GRP` Ціль: MSP430FR5949

## Поточні дані про пам'ять

Поточна карта компонувальника після чистої збірки CCS:

- `RAM`: початок `0x1C00`, довжина `0x0800`, використано `0x0694`, вільно `0x016C`.

- `FRAM`: початок `0x4400`, довжина `0x4000`, використано `0x3C66`, вільно `0x039A`.

- `OTA\_STAGE`: початок `0x8400`, довжина `0x7B80`, використано `0x0000`, вільно `0x7B80`.

- `FRAM2`: початок `0x10000`, довжина `0x3FF8`, використано `0x3FF8`, вільно `0x0000`.

- Вектори/підписи: `0xFF80..0xFFFF`.

Поточний компактний OTA-пакет після додавання OTA dry-run:

- Пакет без `.TI.persistent`: 31476 байт.

- Область проміжного доступу OTA: 31616 байт.

- Поточний запас: 140 байт.

Пакет оновлення не повинен містити `.TI.persistent`, щоб конфігурація полів та лічильники вижили після оновлення прошивки.

## Рекомендована архітектура

Використовуйте поетапне оновлення з невеликим завжди дійсним засобом оновлення:

1. Програма завантажує нове зображення як адресні записи та записує їх в `OTA\_STAGE`.

2. Програма перевіряє глобальний CRC/підпис і записує запис метаданих `OTA\_PENDING`.

3. Після скидання мінімальний оновлювач копіює перевірені записи з `OTA\_STAGE` на їхні кінцеві адреси FRAM.

4. Оновлювач записує вектори переривань/вектор скидання останнім.

5. Якщо перевірка не вдається, оновлювач очищає `OTA\_PENDING` і переходить до поточної програми.

Уникайте прямого самоперепрошивання з основної програми, якщо тільки сервісний технік не може відновити пристрій локально. Втрата живлення під час перезапису запущеної програми може призвести до виходу з ладу контролера.

## Формат пакета

Використовуйте компактні двійкові записи замість необробленого тексту TI-TXT:

```
Заголовок:  
magic\[4\] = "SKMU"  
version = 1  
image\_size = загальна кількість байтів корисного навантаження  
record\_count  
image\_crc32  
flags  
  
Збережений запис:  
address = 20-бітна адреса MSP430, що зберігається в uint32  
length = 1..1024 байти  
crc16  
data\[length\]
```

Транспортний сервер все ще може надсилати пакет як шістнадцяткові фрагменти ASCII, якщо це зручніше для розбору SIM900/HTTP. Фрагменти транспорту та збережені записи навмисно розділені: фрагменти GSM можуть бути невеликими, тоді як збережені записи залишаються більшими, щоб зменшити навантаження на метадані в `OTA\_STAGE`.

## Фази інтеграції прошивки

1. Додайте пакувальник на стороні хоста: `.out` -\> TI-TXT, за винятком `.TI.persistent` -\> компактний пакет OTA.

2. Додати метадані OTA прошивки в постійну FRAM: стан, очікуваний розмір, CRC, зсув запису.

3. Додати записувач прошивки: приймає фрагмент, перевіряє CRC фрагмента, записує в `OTA\_STAGE`.

4. Розширити зашифрований віддалений парсер команд за допомогою команд OTA:

- `ou=version,size,crc;` почати оновлення

- `oc=offset,data\_crc,data;` chunk

- `of=crc;` завершити та позначити як очікуване

- `or;` скинути в оновлювач

1. Додати процедуру оновлення/копіювання, яка запускається із захищеної області або оперативної пам'яті та копіює проміжні записи на кінцеві адреси.

2. Додати політику відкату: не стирати метадані проміжної обробки, доки нова програма не повідомить про успішне завантаження.

## Безпосередні ризики, які потрібно контролювати

- Поточний запас проміжної обробки після OTA dry-run становить лише 140 байт.

- Наступні фази OTA потребують зменшення коду або економнішого транспорту, бо будь-яке помітне збільшення образу вже може не поміститися в `OTA_STAGE`.

- Вектори та скидання мають бути запрограмовані останніми.

- Зміни макета постійних даних повинні бути версіонованими, оскільки `.TI.persistent` зберігається.

- Не використовуйте розмір `.out`; він містить дані налагодження. Важливі лише конвертовані завантажувані байти.

## Поточна реалізована фаза: OTA dry-run

Додано першу безпечну фазу в `parse_remote_command()`:

- `ou=1,<package_size>,<package_crc32>;`

  Починає OTA-сесію тільки в RAM. Розмір має бути `1..31616`, CRC32 передається 8 hex-символами.

- `oc=<offset>,<crc16>,<hexdata>;`

  Перевіряє фрагмент без запису у FRAM. `offset` має дорівнювати кількості вже прийнятих байтів, `crc16` - CRC16-CCITT від decoded `hexdata`. Через поточний AES remote payload у 32 байти практична довжина `hexdata` обмежена 8 байтами за команду.

- `of=<package_crc32>;`

  Завершує dry-run. Стан стає READY тільки якщо прийнято рівно `package_size` байтів і rolling CRC32 збігається з очікуваним.

Ця фаза навмисно не пише `OTA_STAGE` і не виставляє `OTA_PENDING`. Вона потрібна для перевірки протоколу, шифрованого каналу, порядку фрагментів і CRC до появи ризикованого запису прошивки.

### Host-side генератор тестових команд

Додано `tools/make_ota_dryrun_commands.py`. Він генерує plaintext-команди, які сервер має передати через звичайний encrypted remote-command канал:

```
python3 tools/make_ota_dryrun_commands.py --demo 16
```

Приклад малого безпечного тесту:

```
ou=1,16,094C80F1;
oc=0,4792,0102030405060708;
oc=8,F378,090A0B0C0D0E0F10;
of=094C80F1;
```

Для повного dry-run пакета поточної прошивки:

```
python3 tools/make_ota_package.py Debug/skm-8.6.x_GRP.out -o /tmp/skm_8_6.ota
python3 tools/make_ota_dryrun_commands.py -i /tmp/skm_8_6.ota -o /tmp/skm_8_6_commands.txt --negative /tmp/skm_8_6_negative.txt
```

Поточний повний пакет `31476` байт дає `3937` remote-команд при chunk `8` байт. Максимальна довжина команди - `31` символ, тобто вона вкладається в поточний remote payload `32` байти.
